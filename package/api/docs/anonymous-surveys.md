# Anonymous surveys

The **Access → Anonymous** survey setting (`survey.access.anonymous`,
`SchemaSettingSurvey.ts`) guarantees a response cannot be traced to a
participant, either directly or by timing correlation.

## What is guaranteed

For a survey whose active snapshot has `access.anonymous` true, every response:

- stores **no `participantId`** — the field is `null` from creation;
- stores **no `ip` or `referrerUrl`**, regardless of the `data.ip` /
  `data.referrerUrl` settings;
- has every timestamp (`createdAt`, `updatedAt`, `startedAt`, `completedAt`) set
  to the sentinel `ANONYMISED_TIMESTAMP_ISO` (`1971-01-01T00:00:01Z`,
  `veysur-common`), never a real time. `startedAt` / `completedAt` are `null`
  until the response is started / completed.

Only the opaque `sessionId` is kept, and it is not stored against participant
identity anywhere.

## How the participant id is kept out

`JwtParticipant`'s `sessionId` is generated by `randomSessionId()`
(`model/common/randomSessionId.ts`) — a base62 string of the same shape and
length as `genUniqueId()` (so it fits the `CHAR(17)` generated index column),
but built from 12 CSPRNG bytes rather than a BSON ObjectId, so it carries no
embedded timestamp. This applies to every participant session, not only
anonymous ones.

On authentication (`ServiceAuthParticipant.auth`), a survey with
`access.anonymous` is issued a JWT with `participantId: null` — the same shape an
open survey already uses. The participant id therefore never reaches the
response layer. No server-side record links the participant to a session or a
point in time: participant authentication writes nothing to the participant row.

## Enforcement points

- `ServiceSurveyParticipantResponse.save` — loads the snapshot on every save and
  clears the identifying fields and writes sentinel timestamps on both insert
  and update.
- `ServiceSurveyResponse.create` / `update` — the admin CRUD path loads the
  snapshot and applies the same treatment, so a manually authored or edited
  response is anonymised too.

## Resume behaviour

In-progress resume works while the survey app's persisted auth-query cache holds
the JWT (same browser). Re-authentication (cleared cache, another device) issues
a fresh `sessionId` and starts a new response row, and snapshot pinning across a
mid-survey republish does not apply — identical to open-survey behaviour.

## Not retro-active

Enabling the setting affects responses saved from that point on. Responses
recorded earlier keep whatever they stored.

## Display

`isAnonymisedTimestamp()` (`veysur-common`) tests for the sentinel. The admin
response views render "Anonymised" for each timestamp and "Anonymous" for the
participant. CSV exports carry the sentinel date and a blank participant.
